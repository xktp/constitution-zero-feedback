# Feedback and handling

1. Choose a language and form from the [README](README.md#languages). Search existing issues when practical; if the search or forms are inaccessible, email is an equal alternative.
2. Describe one related problem or proposal per issue. Include a public page/document reference and version when known. Distinguish observed behavior from expectations and suggestions.
3. For corrections, quote only what is needed and link to public sources where available. Lack of an external citation does not prevent reporting an accessibility barrier, typo or firsthand observation.
4. Keep discussions respectful and relevant. Do not publish other people's personal information. Screenshots and attachments must be optional and redacted.
5. The project owner can request clarification, relate duplicates, record a decision and link to an implemented change or published correction. Acknowledging a report is not independent review. When closing an issue, explain its disposition; closure alone does not prove a fix was deployed.

## Maintainer setup

- Enable issue notifications for your account through the repository's Watch settings. This is an account preference and is not configured by these files.
- Verify a real submission and notification receipt separately when ready. Do not mark delivery tested merely because the forms or email links exist.
- Keep application code, credentials and private records out of this public repository. Link only to public evidence; do not disclose private source links or records while responding.
- Review translations when changing a form. Keep the same issue category and information requirements across languages. GitHub does not automatically select a form based on browser language; the README links provide explicit selection.

Template format reference: [GitHub Issue Forms](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-issue-forms).
